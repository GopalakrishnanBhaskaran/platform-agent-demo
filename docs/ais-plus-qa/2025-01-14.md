## Q&A

### 1. Wayne: How do you take a custom n8n build from scoping to production so clients can use it without being inside n8n?
- **Scoping starts with discovery.** Ask detailed questions until you have very clear acceptance criteria: integrations, functions, number of users and what data flows through. It should almost feel annoying.
- **Follow-up: Is that question list in the community?** Yes. Nate shared it a few weeks earlier and will point Wayne to the video that walks through it.
- **Follow-up: How do you handle scope creep?** Document everything up front. Nate's proposal doc is reviewed and signed off with the client on the final call. At handover you check it to confirm every milestone was hit.
- **The proposal doc covers:** executive summary, background, requirements and challenges, in scope vs out of scope, tech stack (inputs, outputs, integrations, tools), core components, deliverables, and timeline with milestones. He's building a custom GPT to help draft these.
- **Testing and validation** (trying different models and exposing the agent to as many scenarios as possible) often takes **30–40% of the build** and is hard to estimate.
- **Wireframe every build.** It's clearer for the team and the client than bullet points. Example, a personal assistant build:
  - Phase 1, data ingestion: new items in Notion, email and Dropbox (PDFs) trigger the pipeline. Route by file type, chunk, split and tag metadata, then store in Pinecone.
  - Test chunk size and overlap. Validate the RAG by chatting with a simple agent in n8n, then re-split or re-tag as needed.
  - Phase 2, the assistant: three tools (a Gmail agent, a Notion agent and the vector database). It's triggered from Slack and replies in the same channel.
  - Phase 3: prompting, testing and handover.
- **Follow-up: Will only certain people use it?** For now it's one person's assistant, but plan for the company's long-term goals. Set up Pinecone namespaces early (e.g., an admin sees everything, employees see less). Splitting a default namespace later means deleting and redoing everything.
- Multi-user builds are harder because of authentication. n8n credentials are picked per node from a dropdown, so dynamic credentials need programming workarounds for now.
- **Follow-up: What program is the wireframe in?** Excalidraw. Nate will share both the proposal doc and the wireframe.
- **Follow-up: Do you need a front end?** Usually not. About 4 out of 5 builds are back-end integrations triggered by email or Slack. Keep the client's tech stack slim, since nobody wants new tools or subscriptions.
- Outlook tip: n8n has no built-in node for creating events with attendees, so Nate used an HTTP request to the API endpoint.
- **At kickoff,** the client signs up for the chat models, Pinecone and other paid APIs with their own keys, and pays for usage even during testing. That makes handover smoother.
- The fixed project fee includes **3 months of free maintenance** after handover. It covers handover issues and model upgrades, and keeps the client warm for future projects.

### 2. Gintas: How do you make sure clients can maintain a build after you hand it over?
- It depends on the client.
- **Technical clients** get handover docs that break down what each workflow does, so they can work in it themselves.
- **Or keep it hosted** on Nate's instance for a fixed monthly fee that covers maintenance and updates. That ranges from a couple hundred dollars for a simple build to about **$2,000/month** for large builds with lots of data and more that can break.
- There's no set framework (like "X hours of maintenance a month"). Nate has an open conversation about what the client wants the relationship to look like after the project.

### 4. Gintas: How do you handle clients' fear that internal documents will end up in LLM training data?
- **Nate's answer:** offer to set up a self-hosted instance so the client has full control, and choose models that don't train on inputs.
- His head developer joins those calls to handle the more technical objections.
- Example: a large cybersecurity prospect hosted everything itself (about 1.5 TB of Windows logs and 1 TB of firewall logs a day) and wanted a fine-tuned custom model. Integrations get harder there: you need exposed endpoints, and a custom model has to be wired back into n8n as the agent's chat model.
- **Follow-up: Could there be a framework for choosing a security approach by risk level?** Gintas wants a sheet of common tools, the security options and how to explain them to clients. Nate will work on one with his team.
- **Daniel (IT and data infrastructure background) added:**
  - Think in terms of attack surface, isolation and containerized data flows.
  - On-prem setups he has run used a dedicated network (Tailscale) only for AI traffic between servers. That helps with HIPAA and SOC 2 compliance, auditability and data flow control.
- **Follow-up: If a RAG setup sends an internal PDF to GPT-4o through the OpenAI API, is it used for training?** Daniel: it can be, depending on the policies in place. Enterprise plans run in an isolated environment and don't retain data after the session, while standard plans are pooled.
- **Follow-up: Is turning off training in a $20/month ChatGPT plan enough for a client who wants low cost?** It depends on the data.
  - Not regulated (e.g., not HIPAA): fine.
  - Legal, contract or financial documents: use on-premise hardware with enough compute to run local LLMs.
  - Ask what a data breach would cost, and get a security audit.
- **Follow-up: What about CRM sales data?** It's competitor-sensitive, so process it on-premise where possible.
- **Follow-up: If n8n is on-prem but calls a standard LLM, is that enough?** It depends on how the client classifies sensitive data. For sales data, Daniel recommends an enterprise license.
  - Payment card (PCI) data carries the most liability. A breach can cost $100K to $1M+.
  - Strip PII before data leaves and send generalized summaries instead.
- **Daniel's broader point:** builders need standards for technical debt and "data creep". One of his clients has 100+ complex workflows and a 5-person team that can't fund a full-time maintainer, so plan for auditing and maintainability early.
- He prefers n8n to Zapier for cost and control. It's open source and lets you turn off analytics and update checks, which helps with audits.
- Daniel offered to run an open session on security, and Nate welcomed it.

### 5. Daniel: What are your best practices for getting consistent results from AI agents?
- The same prompt run 10 times can give 10 different answers (temperature). A member suggested caching inputs and outputs, but Nate hasn't tried it.
- **Budget for prompting.** It's most of the 30–40% testing "black box". Estimate how long you'll need, then double or triple it.
- Log inputs and outputs and compare them across models (e.g., GPT-4o vs GPT-4o mini). Nate almost always uses GPT-4o because he likes its output and it isn't expensive.
- **His prompt structure** (he's building a GPT that writes agent prompts):
  - Background and context up front.
  - Each tool's name, what it does and when to use it, including order. Example from an Airbnb booking agent: use the quote tool only after the availability check ran successfully.
  - Clear instructions on the usual order and what to do in different scenarios. If the flow is always linear, use a linear workflow instead of an agent.
  - **Lots of simple examples:** the 5–6 main scenarios, each showing the input and the exact steps. For a booking question: check availability, get a quote, look up the property in the database, then send the reply through the SMS tool.
- In the end it's trial and error.
- **Wayne added: model versions matter.** His autoblogger ignored his length requirements on GPT-4o but worked right away on the dated November 20 GPT-4o snapshot.
- **Nate's RAG debugging example:** a newsletter agent wouldn't include source URLs stored in the vector metadata. The execution logs showed the agent's query to the vector tool never asked for metadata. The fix was telling the agent to always add "return all metadata/URLs" to its vector query.
- **Daniel added:**
  - Learn the vertical's terminology from industry experts and use it in prompts.
  - Use cheaper models for quick, low-stakes queries on non-identifiable data, such as system logs.
  - "It only gives you what you give it."

## Key takeaways
1. **Scope tightly:** lots of discovery questions, a signed proposal with in/out of scope and acceptance criteria, and a wireframe the client can follow.
2. **Budget 30–40% of the build for testing and prompting.** Double or triple your prompting estimate.
3. **Plan for the long term up front** (namespaces, multi-user access), because restructuring later means rebuilding.
4. **Keep the client's stack slim:** back-end integrations triggered from Slack or email, with the client owning the API accounts and keys.
5. **Handover:** a fixed fee that includes 3 months of free maintenance, then handover docs or a hosted retainer (a few hundred dollars to ~$2,000/month).
6. **Match security to data sensitivity:** self-hosted or on-prem setups and enterprise licenses for sensitive data, strip PII before it leaves, and weigh what a breach would cost.
7. **Consistent agents need structured prompts:** context, tool rules with order, scenarios and many examples. Read the logs and pin model versions.
